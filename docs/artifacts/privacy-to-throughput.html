privacy → throughput

A single config flip turns the wallet from a privacy-first consumer funder into a denominated fuel pool built for sustained operator loads — exact-match claims, proactive fan-out top-up, and OpenTelemetry runway metrics. Default stays privacy. Zero behavior change until you opt in.

Why this transition exists

Track P (#935) made funding cost flat in pool size. What remained for high-volume single-operator workloads was the shape of the pool, the work done per request for privacy, and the lack of proactive replenishment.

Privacy is for

Consumer / multi-user wallets

  • Randomized change values break value-link analysis
  • Best-fit funding over variable-value UTXOs
  • Per-request change-count heuristics
  • Replenishment only as a side effect of spends
Throughput is for

Single-operator infrastructure funds

  • Uniform denomination → exact-match every time
  • Skip CountUTXOs; deterministic single change
  • Client-side FuelKeeper fans reserve → fuel
  • Pool/reserve runway gauges for external paging
Privacy trade-off is intentional. Throughput mode makes the operator’s transaction graph fully linkable by design. Use it for infrastructure funds you fully control — never for custodial end-user funds.

What actually changes

Same storage API. Same create → sign → broadcast pipeline. The strategy rewires funding source, change policy, and top-up automation.

The config flip

One field enables the strategy. Throughput knobs are already present under defaults so operators can size the pool before going live.

Before — default
utxo_management:
  strategy: privacy
  # throughput block ignored
→
After — opt-in
utxo_management:
  strategy: throughput
  throughput:
    expected_tx_size_bytes: 668
    expected_output_satoshis: 170
    target_tps: 10000
    expected_confirmation_seconds: 300
    pool_headroom_factor: 1.5
    spend_policy: prefer_mined
    pool_basket: fuel
    reserve_basket: reserve
    fanout_tree_depth: 2
    top_up:
      enabled: true
      interval_seconds: 10
observability:
  metrics:
    enabled: true
    export_interval_seconds: 15

Denomination

Derived as ceil(size/1000 × fee) + output sats (+ commission). Override with denomination_satoshis. Must exceed the marginal fuel-input fee (~15 sat at 100 sat/kb).

Pool target

target_tps × confirmation_s × headroom → ~4.5M default-derived; operators often raise for dual diurnal peaks (~18M for the repo-market profile).

Sustained identity

Fan-out mint capacity per round must cover target_tps × interval × 1.2 so the pool can climb back from low water under load.

Fallback is a feature, not a failure mode. A drained fuel pool degrades to the legacy default-basket path with the same correctness guarantees privacy mode has today. Runway gauges exist so you page before that becomes steady-state.

Three baskets, one money flow

Fuel outputs are ordinary storage-managed change rows with a different basket name — no schema change, no special signing path. Fan-out never spends the pool it is replenishing.

default

Operating funds & remainder

Wallet-payment deposits land here. Throughput remainder change returns here. Fallback funding reads from here.

reserve

Fan-out feedstock

Chunk UTXOs sized to fund a full leaf fan-out. Only fan-out actions spend reserve; regular funding cannot drain it.

fuel

Exact-denomination pool

Uniform sat value (e.g. 240). Hot path claims one (or N for packed actions). Caller-supplied outputs targeting fuel/reserve are rejected.

Shaped change (FuelShape) mints exact-value storage change into reserve or fuel. Leaf shapes fund from reserve; chunk shapes fund from default.

Operator loop after the flip

Enabling throughput is configuration; staying solvent is operations. The FuelKeeper runs in the process that holds the keys.

Set strategy: throughput and size the pool

Derive denomination from expected action shape. Set target_tps and confirmation window so TargetPool covers peak drain with headroom.

Deposit operating funds into default

Ordinary wallet-payment internalizeAction. No special deposit basket API — the keeper moves value default → reserve → fuel.

Run the FuelKeeper

On each top_up interval: if pool < low water, mint toward high water. Immature fuel counts as inventory so rounds don’t over-mint. Hysteresis prevents thrash.

Issue packed actions as usual

No batch endpoint. Batch at the app layer with many outputs per action. Typical 15-output action → one 240-sat claim; large packed actions multi-claim automatically.

Page on runway, not on ErrNotEnoughFunds

Export OTLP metrics. Alert when pool runway < 15m or reserve runway < 1 day. Notification transport stays outside the wallet.

Observability replaces in-process alerting

Metrics ride the same OTLP endpoint as traces. Instruments no-op without a MeterProvider — privacy deployments pay nothing.

Safety properties that make the flip reversible

Guarantees
  • privacy strategy: zero behavior change; dispatch before new paths
  • FundWithConstraints zero-value ≡ legacy Fund
  • Drained pool → fallback, never wrong economics
  • Sweeps/remix never drain the fuel pool
  • Fan-out nets −fee only; shaped outputs stay user funds
  • Rollback = set strategy privacy (basket relabel, no sweep)
Operator duties
  • Keep keeper denomination in sync with server config
  • Use Postgres for rated loads (SQLite single-writer warning)
  • Size reserve against ~2.1 BSV/day fuel burn + ~15% fan-out overhead (repo profile)
  • Own paging transport; wallet only emits well-named telemetry
  • Do not enable for multi-tenant custodial balances
