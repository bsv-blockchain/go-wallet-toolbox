Did the FuelKeeper hold the pool?

Yes, and that is the headline change from every previous attempt. Over the run it produced 30,420 fan-out transactions minting 3,042,000 fuel UTXOs against 3,099,344 consumed — mint tracked burn to within 2% for three hours, with the pool oscillating between its low and high water marks rather than draining. None of the previous failure modes reappeared:

  • No stale-index poisoning. The self-healing claim path never let a spent output block funding; zero dead index rows survived the run.
  • No keeper wedge. Fan-outs kept minting for 3h18m with no ancestry-walk stall.
  • No broadcaster overflow. 3.1M transactions reached the network with none stranded in sending and none swept into aborted.

What actually ended the run

Two resources ran out, and the funds went first:

  • Satoshis, at 07:48:37. Each event burns a 30-satoshi fuel UTXO, so 250/s costs 7,500 sat/s — about 27M satoshis per hour. The run consumed roughly 103M satoshis (~1.03 tBSV) including fan-out fees. The stop was instant and total: the pool hit zero and every subsequent request failed.
  • Disk, some time after. The database grew to 11 GB (~3.5 KB per transaction including indexes) and the host volume reached 100% of 58 GB, which put Postgres into recovery mode. I reclaimed 19.7 GB of Docker images and build cache to bring it back up for this analysis; no data was lost. At this rate the database grows ~1.6 GB/hour, so a full day of running needs ~40 GB of headroom.

One behavioural gap is worth fixing: after funds ran out the stream kept issuing requests for four and a half hours, logging 4.09M failures and adding load for no benefit. It should pause itself when the pool is empty and the wallet cannot refill it.

The right-hand column is the lever. The 30-satoshi denomination exists only because this Arcade host enforces a 100 sat/kb minimum fee; the toolbox already builds valid 1-satoshi-fee transactions at the going network rate. Lowering that host policy cuts the funding requirement about 15× — worth more to long runs than any further code optimisation.
